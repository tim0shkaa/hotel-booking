# Описание решений, принятых по проекту.

## Миграции
В процессе написания обратил внимание, что в ТЗ для booking написано "гости", а не "гость". Соответственно в нашем API вписываются все гости в брони. Но и один человек по идее может быть в нескольких бронях (например если они на разное время). Поэтому создал дополнительно таблицу со связью "много ко многим".
**альтернатива:** Указывать в брони конкретного человека, на которого забронирован номер. Однако в данном случае это не соответствует ТЗ.

Добавил REFERENCES ко всем foreign key, чтобы добавить защиту от добавления неверных данных на уровне БД

timestamptz использовал, так как отели и клиенты могут быть в разных поясах.

NOT NULL для отчества убрал, т к оно не у всех есть.

Также добавил ON DELETE CASCADE, чтобы данные удалялись каскадно в таблице booking_guest.

Остальное стандартно.

## Entity
Создал все классы как data class, т к это просто энтити, переносящие данные между слоями и неизменяемый класс с автоматическими сгенерированными equals(), hashCode() и toString() очень подходит.

Patronymic сделал Nullable аналогично полю в БД.

Первоначально также создал entity для таблицы "много ко многим", но затем убрал за ненадобностью (данные с неё не берутся, а join'ятся к данным из booking сразу в dao). Вместо нее добавил val guests : List\<GuestEntity\> в BookingEntity.

## DTO

По сути dto это объекты, которые представляют данные на входе и выходе API. Есть данные, которые приходят с клиента и данные, которые нужно отправить на клиент. Поэтому я разделил dto на два пакета: response и request. В теле запроса не будет id, оно приходит в URL, поэтому я убрал это поле из request. 
**Альтернатива:** можно было бы объединить response и request для каждого класса в один класс. Получилось бы меньше шаблонного кода, но поле id в каждом классе было бы Nullable. Это бы ухудшило бы читаемость, потому что перестало бы быть видно null id или не null чисто из названия

Остальное по полям и выбору типа класса аналогично Entity.
